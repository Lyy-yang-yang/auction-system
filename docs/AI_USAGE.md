AI 使用说明





本次开发中主要用到的 AI 工具有 DeepSeek、通义灵码，偶尔用智谱清言和文心一言。以下是具体使用情况。

一、各工具的实际用途

DeepSeek（网页 / 对话）





这是我最依赖的协作对象。大部分核心问题都先在对话里讨论清楚，再动手写代码。





项目初期让 DeepSeek 帮我设计了完整的数据库表结构和 API 列表，给出了防超卖的几种并发方案对比，最后选了 Redis 锁 + Lua 脚本 + 乐观锁的组合。

竞价模块的 Redis Lua 脚本、WebSocket 房间管理策略、React Hook 的稳定性问题，都是和 DeepSeek 反复讨论后解决的。

前端组件逻辑，比如号码网格状态切换、倒计时、出价面板的实时更新，很多细节调整都是它给的修正建议。

部署时阿里云环境配置、安全组、Docker 操作等等，几乎每一步都问过它。

最后这份 AI 使用说明的框架也是 DeepSeek 帮忙整理的，然后我自己补充了真实案例和教训。

二、踩过的坑及修复过程

1\. Redis Lua 脚本没处理键不存在





现象：并发出价时偶尔报 Redis 错误，整个竞价卡住。





原因：当时让 AI 生成的 Lua 脚本里，直接用 GET 取最高价然后比较，没考虑 key 为 nil 的情况。Lua 里 nil < number 会直接抛异常。





怎么发现的：写了个测试，用两个请求同时打过去，第二个就挂了。





怎么修：跟 DeepSeek 讨论后，在比较前加了 if not current then，把 nil 当 0 处理。同时把比较的参数统一用 tonumber 转一遍，确保类型不会出问题。修完后再压测就没报错了。

2\. WebSocket 无限重连





现象：后端日志疯狂打印"新客户端连接→注册→加入房间→断开"，前端直接卡死。





原因：React 的 useEffect 依赖里写了一堆变量和回调，每次渲染都销毁旧连接再建新的。加上 StrictMode 帮忙"重放"了一遍，直接变成重连风暴。





怎么修：DeepSeek 给了一套稳定版的 useSocket Hook 代码，核心是用 useRef 存 socket 实例，空依赖数组只执行一次，房间切换用另一个 useEffect 发事件。我替换上去之后立刻安静了。

3\. 房间名不一致导致收不到消息





现象：后端广播了 bid:new，前端啥也收不到，必须手动刷新。





原因：后端广播到 number:${numberId} 房间，前端加入的是 product:${productId} 房间，名字对不上。





怎么修：直接把后端改成广播到产品房间，前端不改，问题消失。

4\. 中文乱码和 Tailwind 丢失





现象：产品名显示"???"，页面样式全丢，背景透明。





原因：数据库编码没在连接字符串里指定，导致存进去的中文读出来是乱码；前端 globals.css 里少了 Tailwind 的 @tailwind 指令，样式完全没生成。





怎么修：DeepSeek 给了排查方向，我自己去查了数据库连接参数，加上了 ?client\_encoding=utf8，然后重新建了一遍测试数据；前端那边检查 globals.css，补上指令，清缓存重启，样式回归正常。

5\. 库存显示 "0/" 和 "N度" 乱码





现象：产品卡片上库存显示 0/ 没有分母，加价幅度显示 N度。





原因：数据库里有个产品 total\_stock 是 NULL，前端直接拼接就缺了；i18n 替换中文时，正则没覆盖带特殊字符的内容。





怎么修：后端查库存时用 COALESCE(total\_stock,0) 兜底；前端替换规则改成只要内容包含"超越"就翻译，不再用严格匹配。

6\. 竞价结束时间判断前后端不一致





现象：前端倒计时归零后，用户还能出价成功，但后端日志显示竞价已结束。





原因：前端用 new Date(bidEndTime) 转换时间，没考虑时区偏差。服务器是 UTC，浏览器是东八区，差了 8 小时。





怎么修：后端返回时间时统一用 ISO 格式带时区偏移（如 2025-05-10T18:00:00+08:00），前端不再自行转换。倒计时也改成用服务器时间差来计算，不依赖本地时钟。

7\. 并发出价偶尔出现相同最高价





现象：两个人几乎同时出价，数据库里出现了两条 is\_winning: true 的记录。





原因：原来出价逻辑里先把旧的最高价标记为 false，再创建新记录，两步之间没有锁保护。两个请求同时执行到"标记旧记录"那步，都觉得自己是新的最高价。





怎么修：把整个"取消旧最高价 + 创建新出价 + 更新产品价格"包进事务里，并且加上了 SELECT FOR UPDATE 行锁。改完之后压测再没出现过重复最高价。





三、Prompt 怎么写的：从踩坑到学乖

案例 1：数据库设计





最开始我写的是：





帮我设计一个竞价系统的数据库





结果 DeepSeek 给了一堆表，字段类型全是 VARCHAR，价格用的 FLOAT，也没说索引的事。拿过来发现金额计算精度丢失，改了好几处。





后来我改成：





竞价系统数据库设计，6 张表：用户、产品、号码池(1-100)、出价记录、订单、通知。金额字段必须用 DECIMAL(10,2)，号码表需要 (product\_id, number) 唯一约束。每张表标注索引和关联关系。





这次返回的结构直接能用，只微调了几个字段名。

案例 2：竞价核心逻辑





第一次问：





帮我写竞价出价的函数





拿到的代码没有并发处理，没有事务，连参数校验都不全。





拆细了再问：





Express + Knex + TypeScript 环境。写 placeBid 函数，参数是 productId/numberId/userId/amount。要求：1) 数据库事务包裹 2) 先查产品状态和竞价截止时间 3) 校验出价 >= 当前最高价 + minBidIncrement 4) 标记旧的 isWinning 为 false 5) 创建新出价记录 isWinning 为 true 6) 更新产品 currentPrice 7) 返回新出价和被超越用户 ID





这次生成的代码逻辑完整，只补了一个限流检查。

学到的经验





模糊的 Prompt 只能拿到框架，细节全靠自己补。不如一开始就把约束条件说清楚。

太长的 Prompt 一次性让 AI 生成整个模块，出错率很高。改成"先类型定义，再单个函数，最后组装"，反而快。

把报错信息原样贴给 AI，比自己描述问题有效 10 倍。





四、手动写的部分（AI 搞不定的）





模块	为什么没让 AI 写

Redis 分布式锁（acquireLock/releaseLock）	AI 给的方案要么太简单没考虑锁超时，要么用了第三方库我不想引入。最后按 Redis 官方推荐的模式自己写了 SET NX EX + Lua 释放。

竞价事务的行锁策略	AI 一直分不清 knex / SQL 什么时候会加行锁什么时候不会，反复试了几版都有并发漏洞。自己查了 knex 文档，用 FOR UPDATE 加行锁才解决。

next-intl 国际化配置	AI 训练数据里 next-intl 3.x 的用法太少，一直给我 2.x 的写法。我直接看的官方文档手动配的。

Docker Compose 的网络和依赖	容器启动顺序、健康检查、网络别名这些，AI 每次给的都不一样，前后端连不上数据库的问题折腾了俩小时，最后自己照着 Docker 文档改的。

前端号码网格的移动端适配	AI 生成的 10x10 网格在手机上溢出，改成 grid-cols-5 sm:grid-cols-10 的响应式方案是我自己写的。





五、各场景 AI 代码使用比例





模块	AI 生成占比	说明

数据库 Schema	\~70%	基础结构 AI 生成，字段类型和约束手动调整

后端 CRUD（产品/订单/通知）	\~85%	这部分套路化，AI 生成的质量不错

竞价核心逻辑	\~40%	并发和事务部分 AI 反复出错，最终自己重写大半

Redis 锁 + Lua 脚本	\~20%	AI 给的参考方案，核心代码自己写

WebSocket 配置	\~50%	基础连接 AI 生成，房间管理和重连逻辑手动改

前端页面	\~60%	布局和样式 AI 辅助，交互逻辑自己调整

i18n 配置	\~30%	AI 基本没帮上忙，主要是查文档

总体估算，项目里大概 55-60% 的代码有 AI 参与（生成后修改或直接使用），剩下 40% 是我自己写的。





六、总结





这次开发里，AI 帮我节省了大量写 CRUD、搭组件、翻译文案的时间，大概有六七成的基础代码是 AI 生成的。但在并发逻辑、WebSocket 状态管理、部署坑这些需要整体理解的地方，AI 经常出问题。我的处理方式一直是：先让 AI 快速生成，然后自己测，发现问题再带上下文去问，迭代修正。





整个项目能在 48 小时内完成并上线，AI 贡献非常大，但最终的工程质量是靠我自己把关的。
